# Qwen-Image 2.1 テキスト画像生成＆超高解像度 (2K) 実機検証ガイド

Alibaba が 2026年9月20日にリリースした最新の画像生成基盤モデル **Qwen-Image 2.1** を用い、**Google Cloud (NVIDIA L4 24GB Spot インスタンス)** 上で「1K（1024×1024）」および「2K（2048×2048）」の生成速度とリソース消費量を実機検証した技術ノウハウである。

## 🧠 実機検証で得られた重要知見

### 1. ホスト側 RAM（16GB vs 32GB/64GB）と生成速度の関係
* **結論: ホスト RAM を増やしても、サンプリング（生成）速度そのものは向上しない。**
* **理由**:
  * `pipe.enable_model_cpu_offload()` を使用した場合でも、20ステップの拡散サンプリングループ中は **DiT モデル（約14GB）が GPU VRAM 上に常駐したまま計算**される。
  * ステップ毎に CPU ➔ GPU のメモリ転送が発生しているわけではないため、ステップ速度（3.1秒/step や 16.8秒/step）は純粋に **NVIDIA L4 GPU の CUDA/Tensor コア計算性能** で律速される。
* **RAM を増やすメリット**:
  * モデル全体（約28GB）をディスクスワップに頼らず物理 RAM 上で保持できるため、**スクリプト起動からサンプリング開始までの初期ロード時間が十数秒短縮**される。
  * RAM 使用率 99% による OS のメモリ圧迫が解消され、長時間の安定稼働が可能になる。

### 2. 2K（2048×2048）生成における VAE デコードの留意点
* 2K 解像度では、20/20ステップの拡散計算（潜在変数 Latent 256×256）は 16.8GB VRAM で安定して完走する。
* しかし、最後の VAE デコード（Latent から 2048×2048 の非圧縮画像への展開）時に約 4.5GB の追加テンソルが瞬間的に要求される。
* DiT モデルが GPU 上に残ったままだと合計 17.9GB + 4.5GB > 22GB となり VRAM 溢れ（OOM）を起こすため、**サンプリング完走後に DiT モデルを確実に CPU へ退避（または hook を解除）して VRAM を空けた状態で VAE デコードを実行する（ステージド・メモリデコード）** のがベストプラクティスである。

## 🚀 実行方法 (ワンコマンド)

```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8;

# 1K (1024x1024) 高速生成
.\models\qwen_image_2_1\gcp\run_cloud.ps1 `
    -Width 1024 -Height 1024 -Steps 20 `
    -OutputFilename "qwen_1k.png"

# 2K (2048x2048) 超高解像度生成
.\models\qwen_image_2_1\gcp\run_cloud.ps1 `
    -Width 2048 -Height 2048 -Steps 15 `
    -OutputFilename "qwen_2k.png"
```
